# Decide what to package

Start with the request, the governing requirements, and examples of the work. Identify what each recipient must be able to do with the result. Treat two results separately when the recipient can accept either on its own. Record any names, boundaries, or delivery methods the requester requires. For an edit, inspect the existing entry, its resources, and the places that use them.

## Choose where the instruction belongs

For each result, identify the decision or action that needs to change. Trace a reported failure to the point where the worker lacked information, chose an action, or accepted the result. Apply the first row that settles that part of the request.

| Situation | Action |
| --- | --- |
| A named authority must make a decision and has not delegated it. | Obtain that decision. If the assignment is to discover who holds authority or to design a rule, continue with that job. |
| A settled rule must hold on every covered operation and its inputs determine the outcome. | Enforce it where the operation occurs. Check a permitted case and a prohibited case. |
| A maintained source supplies the answer or an existing operation performs the work. | Use that source or operation. Correct its interface if the failure originates there and the change is authorized. |
| An instruction applies to every assignment, or a method must reach the worker on every occurrence. | Put a universal instruction in standing guidance. Put mandatory delivery in the workflow. If the request also commissions a reusable method, account for both results. |
| This is a single assignment with no identified reuse. | Complete the work in that assignment. |
| The current workflow already delivers the required result, and the request leaves the intervention open. | Report the evidence and keep the current workflow. If adequacy is unknown, examine an ordinary attempt before prescribing a remedy. |
| A recurring job has a cue the worker can see in time, and a reusable method or resource changes a decision or action. | Consider a skill. State the cue, what the worker will do differently, and what the recipient can check. |

Support each added obligation with its governing requirement or dependency. Label a new approval, record, or check as a proposal until the owner adopts it.

## Decide the boundaries

Try one procedure on the actual cases. Group them if the same question determines the action and the same kind of observation checks the result in each case. Different inputs or owners can be branches. Split independently requested results when they need different decisions or completion checks. A shared source can serve both. Honor a prescribed entry point by linking to the distinct procedures it must deliver.

Compare plausible groupings after accounting for every required result. Among equally complete groupings, choose the fewest separately invoked entries, then the least duplicated instruction. Use an adopted project convention for equivalent arrangements. If a choice changes the deliverable, identify the deciding fact and retrieve it or obtain it from the person responsible. Try the boundary on a different subject with the same decision and on a similar request that calls for a different action.

Once the jobs are defined, compare them with existing entries. Reuse an entry that already serves the same decision and audience. Revise it for a missing action or check. Before retiring an entry, identify the callers that still depend on it.

## Write and check the package

Use the destination project's vocabulary. This collection has an [English naming convention](references/naming.md). In the description, name the work and the situation that makes the procedure useful. Include a nearby exception when it helps the worker distinguish the jobs.

Write the body in execution order. Identify the input that governs the choice, the condition that changes the action, and the observation that establishes completion. Link to a maintained fact or supporting procedure at its point of use. Put the basis for consequential rules in the authoring record. Add a script when repeating an operation through code will produce a required result.

For an edit or consolidation, check the result from the recipient's installed entry point. Exercise each promised route, including its references, templates or commands. Update consumers that use a moved path. Verify that the retained behaviors still work and validate the package with the intended harness.

When evaluating a package or making a claim about its reliability, use the [discovery and delivery checks](references/evaluation.md).
